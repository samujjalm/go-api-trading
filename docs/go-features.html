Concurrency · 1

Every connection gets its own goroutine

The service never writes go to handle a request. net/http starts a goroutine for every accepted connection, so a hundred clients placing orders at once means a hundred handlers running in parallel across all CPU cores. A goroutine starts with a few kilobytes of stack, which is why this is cheap enough to do per connection.

That makes the important question what those goroutines share. Anything two goroutines can write at the same time needs synchronisation. This service avoids the problem by design: everything shared is either read-only or built for concurrent use, and everything mutable lives inside one request.

Six orders arrive together: who waits?

Matching is the one place where requests really do compete: two buyers must not both fill against the same 100 shares. Below, six goroutines start within a few moments of each other. Switch the locking strategy and replay to see who runs in parallel, who queues, and what goes wrong without a lock.

Go code (decode, validate, respond) blocked waiting for the lock transaction: match + settle read-only query overlaps another order on the same book

Durations are illustrative units, not measurements.

Why not a sync.Mutex?

A Go mutex only coordinates goroutines inside one process. A fintech service runs several replicas behind a load balancer, and each would have its own mutex. Two replicas could then match AAPL orders at the same time.

A Postgres advisory lock lives in the database, which every replica shares. It also ends with the transaction, so a crashed process can't leave it held forever. The rule of thumb: sync protects memory, the database protects money.

Concurrency · 3

Channels, select and a clean shutdown

What happens on docker stop

in order
  1. Two goroutines are running. main is parked in select; the server goroutine is inside ListenAndServe, spawning request goroutines.
  2. Docker sends SIGTERM. signal.NotifyContext cancels ctx, so its Done() channel closes.
  3. select wakes up on the ctx.Done() case. A select blocks until one of its channels is ready.
  4. Shutdown stops accepting connections and waits for in-flight requests to finish, so an order mid-transaction commits instead of being cut off. After 10 seconds it gives up.
  5. ListenAndServe returns ErrServerClosed into errCh. The channel has a buffer of 1, so that send never blocks even though nobody reads it now. An unbuffered channel here would leak the goroutine.
  6. Deferred calls run in reverse order: cancel(), then pool.Close(), then stop(). Last in, first out means the pool closes only after the server has drained.

In-flight requests keep running during shutdown because their contexts come from the server, not from ctx. Cancelling the signal context doesn't cancel them.

Concurrency · 4

context.Context carries deadlines and request data

Almost every function in the service takes ctx context.Context as its first argument. A context does two jobs:

Cancellation flows down. If a client disconnects, r.Context() is cancelled. Every query passed that context is abandoned by pgx and the transaction rolls back, so no goroutine keeps working for a caller who has gone.

Request-scoped values ride along. Middleware attaches the request ID logger and the authenticated user ID with context.WithValue, keyed by an unexported type so no other package can collide with or forge them.

Contexts form a tree. Deriving a child never changes the parent, so they are safe to share across goroutines.

Concurrency · 5

select with a timer: retrying deadlocks politely

Two orders on different symbols can lock the same two users' balances in opposite orders. Postgres spots the cycle and aborts one transaction with error 40P01. WithTx treats that as retryable: it waits a short, randomised backoff and runs the transaction body again. The wait is a select, so a cancelled request stops retrying immediately instead of sleeping.

attempt 1deadlock_detected (40P01), rolled back
backoff5ms × attempt + random jitter
attempt 2commits; caller never sees the deadlock

Details worth copying

Loop variables are per iteration since Go 1.22. Each goroutine's w is its own copy. Before 1.22 all eight closures would share one w, a classic bug that needed w := w.

Deterministic randomness. Each worker seeds its own math/rand/v2 generator from its index, so a failing run can be reproduced. Workers never share a generator, so it needs no lock.

The race detector. make test runs with -race, which instruments every memory access and fails the test if two goroutines touch the same variable without synchronisation. It catches races the invariants can't see.

Real deadlocks happen here, and the test logs how many Postgres detected and the retry loop absorbed, while every money invariant still holds.

Beyond concurrency

Language features, as used here

Interfaces are satisfied implicitly

adapters/postgres/store.go

No implements keyword: a type satisfies an interface by having the methods. Both *pgxpool.Pool and pgx.Tx fit this small interface, so every repository works inside or outside a transaction. The var _ line makes the compiler check the adapter still satisfies the port.

Struct embedding

adapters/http/middleware.go

Embedding http.ResponseWriter promotes all its methods. The recorder overrides only WriteHeader to remember the status for the access log; everything else passes straight through. This is composition, not inheritance.

Errors are values

domain/errors.go · http/respond.go

Functions return errors; callers decide. %w wraps an error while keeping it inspectable. errors.Is walks the chain for a sentinel, and errors.As pulls out a typed error. The HTTP adapter maps them to status codes in one place.

defer and recover

adapters/http/middleware.go

defer runs when the function returns, even during a panic. A deferred recover() stops the panic and turns it into a 500. The domain panics deliberately when a money invariant breaks; pgx's deferred rollback then undoes the transaction.

Functional options

app/options.go

An option is a function that edits a config struct. Constructors take ...Option, so production code calls NewAuthService(store, …) while tests add WithClock(fake) to control token expiry. Adding an option never breaks existing callers.

Generics

adapters/postgres/orders.go

pgx.CollectRows is generic over the row type: give it a mapper that returns *domain.Order and you get []*domain.Order, type-checked. The built-in generic min and max (Go 1.21) appear in matching and pagination.

Method values

adapters/http/account_handlers.go

A method bound to its receiver is an ordinary function value. Deposit and withdraw share one handler body by passing s.account.Deposit or s.account.Withdraw as the operation.

//go:embed

adapters/postgres/db.go

The SQL migrations are compiled into the binary as a read-only filesystem. That's how the API runs in a distroless image with no files besides itself: one binary carries its schema.

Struct tags

adapters/http/trading_handlers.go

Tags are metadata the encoding/json package reads by reflection. They name the JSON fields and drop zero values with omitempty, such as a market order's price. The DTOs live in the adapter, so the domain types stay free of JSON concerns.

Pattern routing (Go 1.22)

adapters/http/server.go

The standard library router matches methods and path wildcards, so no web framework is needed. A wrong method gets 405 automatically, and r.PathValue reads the wildcard.

Table-driven tests

domain/matching_test.go

The idiomatic Go test: a slice of cases, one loop, t.Run per case for a named subtest. t.Helper() points failures at the caller's line, and t.Cleanup runs the ledger check after every trading test.

Build tags

*_test.go with //go:build integration

A build constraint on the first line keeps a file out of the build unless the tag is set. go test ./... stays fast and needs no database; make test-integration adds -tags integration to include the Postgres tests.
